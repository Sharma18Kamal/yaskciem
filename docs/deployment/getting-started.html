YASK-CIEM: setup and cloud sign-in

Start here after installing YASK-CIEM. This guide opens locally in your browser and needs no internet to read. Signing in and scanning require network access.

Using the native MSI or Setup EXE? The required .NET 10 runtimes are already included. You do not need the .NET SDK or a separate runtime installer. Do not install PostgreSQL on each Desktop PC. Desktop stores its local results in SQLite; PostgreSQL belongs on the separate License Server.
Your first scan
  1. Install and collect your organization settings
  2. Sign in to YASK-CIEM and activate the trial
  3. Sign in to Azure, AWS or Google Cloud
  4. Select an account and run a read-only scan
Troubleshooting | Administrator: License Server and PostgreSQL

1. Install and collect your organization settings

  1. Use the installer supplied through your organization's trusted release channel. Verify the publisher/signature. Do not bypass Windows publisher warnings or import a development certificate on a customer PC.
  2. Close YASK-CIEM before upgrading. Run the MSI or Setup EXE and approve the Windows administrator prompt if authorized. Installation does not delete your existing scan data.
  3. Open YASK-CIEM from Start. Run the app as your normal Windows user, not as administrator.
  4. Ask your administrator for the four values below. If no server exists yet, the administrator must complete server setup first.
SettingExample (replace placeholders)
License Server HTTPS URLhttps://ciem.example.org/
Microsoft Entra tenant IDYour organization's tenant GUID
Desktop application client IDThe Desktop public-client GUID, not the API client ID
API delegated scopeapi://<api-client-guid>/access_as_user

Install only the official cloud CLI tools for the providers you will scan. Follow your organization's software-installation policy:

  • Azure CLI installation (internet required)
  • AWS CLI v2 installation (internet required)
  • Google Cloud CLI installation (internet required)

These CLI tools, cloud credentials and the License Server are not installed or provisioned by the Desktop installer. Use dedicated, approved read-only identities.

2. Sign in to YASK-CIEM and activate the trial

Open PowerShell as the Windows user who will use Desktop. Replace the three placeholder values below with the administrator-provided settings, then run:

[Environment]::SetEnvironmentVariable('YASK_CIEM_API_BASE_URL', 'https://ciem.example.org/', 'User')
[Environment]::SetEnvironmentVariable('YASK_CIEM_ENTRA_CLIENT_ID', '<desktop-client-guid>', 'User')
[Environment]::SetEnvironmentVariable('YASK_CIEM_API_SCOPE', 'api://<api-client-guid>/access_as_user', 'User')
  1. Save your work, close YASK-CIEM, and sign out of Windows and back in so that newly launched programs receive the settings. Reopen YASK-CIEM from Start.
  2. Open Organizations > Organization > Sign-in, enter the actual tenant GUID, then select Sign in. Complete the browser sign-in. If approval is required, ask your Entra administrator; do not bypass consent.
  3. Select Start 30-day trial, then Refresh license. Confirm the header shows an active trial or license.
There are two different sign-ins. Organizations sign-in authenticates you to the YASK-CIEM API, even when scanning only AWS or Google Cloud. Cloud Accounts sign-in authenticates the provider CLI. Neither replaces the other. Reinstalling the app does not restart the tenant's trial.

3. Sign in to your cloud

Use a new PowerShell terminal after installing a CLI. Run these commands under the same Windows user as YASK-CIEM. Only connect providers and scopes approved by your administrator. Signing in does not grant missing cloud permissions.

Microsoft Azure

  1. Ask the Azure administrator for read-only access, normally Reader on the approved subscriptions. Directory/Graph and PIM reads need separate approved permissions and consent; subscription Reader alone does not provide them.
  2. Verify the CLI and sign in, replacing the tenant and subscription placeholders:
az --version
az login --tenant '<tenant-guid>'
az account list --output table
az account set --subscription '<subscription-guid>'
az account show --output table

In YASK-CIEM, open Cloud Accounts, select Azure Connect, and complete or reuse the CLI sign-in. Continue to your first scan. Never grant Owner or Contributor just to make a read-only scan work.

Amazon Web Services

Prefer IAM Identity Center SSO with an administrator-approved read-only permission set. Ask for the SSO start URL, SSO region, account and permission set.

aws --version
aws configure sso --profile ciem-audit
aws sso login --profile ciem-audit
aws sts get-caller-identity --profile ciem-audit
aws configure list-profiles

Repeat with a distinct profile name for each approved account/permission set. In Cloud Accounts, select AWS Connect. The current launcher may open aws configure --profile yask-ciem, which configures IAM keys, not SSO. If using SSO, prepare the profiles above and close that unused terminal; do not create long-lived keys merely because it opens. The app can detect working SSO profiles. Verify account and profile names before selecting rows for a scan.

Google Cloud

Ask the administrator for approved read-only project/IAM access and Cloud Asset Inventory permissions. The administrator must enable the required API; the scanner does not do that. Inherited policies and audit logs may need additional reads.

gcloud --version
gcloud auth login
gcloud auth list
gcloud projects list
gcloud config set project '<project-id>'
gcloud projects get-iam-policy '<project-id>' --format=json

In Cloud Accounts, select Google Cloud Connect. The app uses the active gcloud account; Application Default Credentials login is not a replacement for this check.

Optional: Kubernetes

Install kubectl and the required authentication plugin. Have your administrator supply an approved, read-only kubeconfig/context. The app does not create contexts or refresh cluster credentials. Check the context with kubectl config get-contexts, then select the intended Kubernetes rows during discovery. Selecting a cloud account does not select all its clusters. Never grant cluster-admin just for scanning.

4. Run your first read-only scan

  1. Confirm the header shows an active trial/license. Connect each intended provider in Cloud Accounts for this app session; cached CLI credentials alone do not select a provider.
  2. Open Dashboard > Discover accounts.
  3. Start with one approved non-production account, project, subscription or cluster. Inspect the provider, account ID, AWS profile/permission set and Kubernetes context. Do not use Select all for the first test.
  4. Select Scan Now. Use Stop Scan to cancel.
  5. Review completion and per-source coverage. Denied, Unavailable, Unsupported, Unknown or partial results are evidence gaps, not a clean security assessment.
  6. Review Risk Findings, Recommendations, Effective Access and Scan History. Use Generate Report, choose JSON, CSV, HTML, XML, PDF or Excel, then select the save location.

Discovery, scans and offline what-if analysis do not change cloud resources. Separate cloud-administration/JIT workflows can write when explicitly configured and approved; leave them disabled for initial onboarding. Protect reports and exported evidence under your organization's security policy.

Use Find workspace in the left menu. Long workspaces are divided into named subtabs that stay above the scrolling content. Organizations groups these under Organization, Scans, Evidence, Security, Alerts, Admin, and People & audit. Select an organization under Organization > Organizations; account bindings are under Admin > Account bindings, and members under People & audit > Members.

The fixed Jump to section selector opens the matching group and subtab, including collapsed sections. Back to top returns to the beginning of the current subtab. Form drafts and selections are preserved when switching tabs; switching tabs alone never starts a scan or cloud operation. The mouse wheel scrolls the area under the pointer, then hands off to the containing page at its edges; closed dropdown values do not change.

Troubleshooting

ProblemWhat to do
API not configuredCheck all three user environment variables. Use the HTTPS API URL, not a Blob URL or a different PC's localhost. Relaunch with refreshed environment settings.
Organizations Sign in is disabledEnter a valid tenant GUID.
Consent/admin approval neededAsk the Entra administrator to review the requested permissions and tenant policy.
401 or 403 from the APIAsk the administrator to check API audience/scope, tenant and organization membership. Cloud CLI sign-in is separate.
Trial unavailable or expiredCheck server availability and Refresh license. Obtain an approved entitlement; do not delete trial history or reset the database.
CLI not found or cloud not connectedInstall the official CLI, open a fresh terminal, verify the commands above, then select Connect under the same Windows user.
Cloud AccessDenied or missing accountsCheck the specific approved read permissions and scope. For AWS, verify a working SSO profile for each account; listing an organization does not grant member-account access.
TLS/certificate failureHave the administrator correct certificate trust, hostname and validity. Do not bypass TLS validation.
Server readiness 503The administrator must check schema, database, workers and immutable archive readiness. Liveness 200 alone is insufficient.

Desktop logs: %LOCALAPPDATA%\CloudEntitle\Logs. Share only sanitized error codes, timestamps and affected scope. Never share tokens, credentials, Authorization headers or unredacted sensitive exports.

Administrator: License Server and PostgreSQL

Set this up once per environment, not once per Desktop. Users joining an existing installation need only its approved settings. The Desktop installer does not install or configure the server, PostgreSQL, cloud identities, archive storage or a trial.
  1. Choose an organization-managed server and obtain the matching License Server bundle. Native Desktop packages and the self-contained server bundle already include their .NET 10 runtimes. Source builds require the repository-selected .NET 10 SDK.
  2. Install PostgreSQL 15+ on a protected database host using the organization's approved installer. Keep it private; do not expose port 5432 to the internet. Establish backups and separate DBA, runtime and archive identities.
  3. Back up existing data before upgrades. Using the DBA identity, apply every numbered SQL migration shipped with the matching release in filename order, including subscriptions. Follow the package manifest where provided. Sequence gaps are allowed; do not invent, rename or renumber scripts. Production startup does not apply migrations. Never delete trial history.
  4. Register separate Microsoft Entra API and Desktop public-client applications. Configure v2 API tokens, expose access_as_user, authorize the Desktop delegated permission, and set its interactive redirect URI to http://localhost. Complete consent according to tenant policy. The Desktop public client does not need a client secret.
  5. Configure the API tenant/client settings, database secrets, audit integrity keys, approved immutable archive, trusted HTTPS and process supervision. A production Azure archive needs an authorized host managed identity; it cannot inherit a Desktop CLI login. Scheduled scans need separate server-identity CLI authentication.
  6. Verify the approved HTTPS endpoint: /health/live and /api/v1/readiness must return 200 after complete provisioning. Unauthenticated subscription requests must return 401. Test backup/restore and archive verification before production sign-off.
  7. Give operators the HTTPS URL, tenant GUID, Desktop client GUID and API scope. Do not distribute server secrets.

For detailed administrator permissions, server hosting, database installation, local development and archive procedures, see the complete installation guide (internet and repository access required; use the documentation matching your release).
